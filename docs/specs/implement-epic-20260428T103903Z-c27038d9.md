## Problem statement
The project has a well-defined root epic in Beads, but the implementation scope is spread across many child issues covering foundations, domain modeling, weather providers, Telegram flows, LangGraph orchestration, persistence, observability, and deployment. Without a single implementation spec, agents working in fresh contexts risk solving tasks in isolation, drifting on interfaces, or making incompatible decisions around data contracts, runtime boundaries, and acceptance criteria. This matters because the MVP only succeeds if deterministic weather/rule workflows, Polish-language UX, and homelab deployment fit together as one coherent system. Assumptions used for this spec: the target epic is `weather-agent-778`; MVP scope is defined by that epic's definition of done plus its current child tasks; unresolved operational choices are treated as open questions, not blockers for implementation planning.

## Goals
- Deliver the `weather-agent-778` epic as a self-hosted Telegram weather AI agent for Polish-language use.
- Define the implementation slices required to move from empty repository to runnable MVP.
- Preserve deterministic behavior for time resolution, rule evaluation, notification delivery, and persisted explanations.
- Standardize core contracts across Telegram, LangGraph, database, and weather-provider boundaries.
- Keep learning-oriented integrations with LangGraph and LangSmith without making runtime correctness depend on the LLM.

## Non-goals
- Supporting languages other than Polish.
- Supporting timezones other than `Europe/Warsaw`.
- Building a web UI, mobile app, or non-Telegram interaction channel.
- Adding per-location unit preferences in the MVP.
- Integrating optional future weather providers such as OpenWeather or AccuWeather beyond documented extension points.

## Requirements
### Functional
- The system must authorize Telegram users before allowing weather, location, or rule operations.
- The bot must maintain thread-scoped context using `chat_id + message_thread_id`, with `chat_id` fallback when no topic is present.
- Users must be able to create, read, update, and delete named locations with aliases and coordinates.
- The system must resolve Polish natural-language time ranges such as `dziś`, `jutro`, `weekend`, and `majówka` into explicit Warsaw-time ranges.
- The weather Q&A flow must resolve location and time deterministically, fetch forecast data through a `ForecastProvider`, and answer in concise Polish while naming the resolved location and time range.
- The MVP forecast source must be Open-Meteo DWD ICON, normalized into shared forecast contracts and persisted with raw payloads.
- The system must fetch and normalize current synoptic observations from IMGW when needed for user-facing answers or status flows.
- The system must fetch and surface official IMGW warnings for relevant saved locations.
- The rule workflow must let the LLM propose CEL expressions, present both CEL and human-readable meaning, require explicit user confirmation, and persist only validated expressions.
- The system must support rule CRUD, short rule IDs, snooze, cooldown, deduplication, and disable/delete flows.
- Rule evaluation must run deterministically against persisted weather snapshots and must not call the LLM at runtime.
- Notifications must include stable short rule/event identifiers and support later explanation requests based on stored evaluation and audit data.
- The application must persist locations, forecasts, observations, warnings, rules, evaluations, notification events, audit records, and thread memory in PostgreSQL plus TimescaleDB where time-series storage is appropriate.
- LangGraph must orchestrate the conversational workflow, including weather Q&A, rule proposal/confirmation, context handling, and error paths.
- LangSmith tracing and eval hooks must be wired for graph/tool visibility and learning feedback within low-cost limits.
- The project must run locally through `docker compose up` with documented configuration, health checks, and operational basics.
- The repository must include automated tests for units, integration seams, and at least one end-to-end mocked MVP scenario spanning Telegram input through explanation output.

### Non-functional
- Runtime correctness must favor transparent failure over fabricated weather data or fake confirmations.
- External provider integrations must use typed errors, timeouts, and retry policies where appropriate.
- Core contracts must remain independent from Telegram and LangGraph where domain reuse is expected.
- All user-facing answers and prompts must be in Polish.
- Secret handling must be explicit, typed, and excluded from logs.
- Logs, traces, and audit records must be sufficient to explain notifications and diagnose failures after the fact.
- The design must support fresh-context contributors by keeping ADRs, vocabulary, and interface boundaries documented.
- The initial deployment target is a single homelab Docker Compose environment, not horizontal scale.

## Interfaces / data contracts
- `TelegramUpdate -> ContextKey`: map inbound Telegram messages into a thread context key of `chat_id + message_thread_id`, falling back to `chat_id`.
- `LocationRef`: canonical location object containing ID, name, latitude, and longitude for downstream provider and persistence use.
- `TimeRange`: explicit start/end datetimes in `Europe/Warsaw`, produced by deterministic resolution rather than model inference.
- `ForecastProvider`: async contract returning normalized forecast results and preserving source payloads for Open-Meteo DWD ICON.
- `ObservationProvider`: async contract returning normalized IMGW synoptic observations, ideally linked to nearest station metadata.
- `WarningProvider`: async contract returning normalized official IMGW warnings for a location and time range.
- `ForecastPoint`, `ForecastResult`, `ObservationPoint`, and `WeatherWarning`: normalized weather records with unit-qualified fields and `None` for missing values.
- `Rule`: persisted notification rule with short ID, validated CEL expression, human-readable summary, scope metadata, lifecycle state, cooldown, and snooze settings.
- `PendingConfirmation`: thread-scoped record that binds a proposed rule change to the requesting Telegram context until explicit user confirmation or rejection.
- `EvaluationEvent`: deterministic rule-evaluation result tied to forecast snapshot inputs, rule ID, timestamps, and explanation-ready evidence.
- `NotificationEvent`: persisted outbound notification record containing short IDs, delivery metadata, dedupe key, and explanation linkage.
- `AuditRecord`: durable trace of important user and system actions, especially rule mutations, evaluation outcomes, and notification sends.

## Acceptance criteria
- A fresh environment can start the MVP stack with `docker compose up` after configuration is provided.
- Authorized Telegram users can ask Polish weather questions about saved locations and receive answers that state the resolved location and time range.
- The bot can create and manage named locations, global settings, and thread-scoped memory needed for follow-up interactions.
- The system resolves supported Polish time phrases deterministically, with tests covering edge cases such as weekends and `majówka`.
- Open-Meteo forecast data is fetched, normalized, persisted, and reused by deterministic rule evaluation.
- IMGW observations and official warnings are retrievable through provider abstractions and surfaced through application flows.
- Rule proposal requires user confirmation, rejects invalid CEL, and stores only validated deterministic rules.
- Scheduled or event-based rule evaluation produces persisted evaluation evidence and notification records without LLM runtime dependence.
- Notifications include short IDs that allow a later “why did I get this?” explanation based on stored data.
- LangGraph traces and LangSmith instrumentation expose graph path and tool calls for the main conversational flows.
- Unit, integration, and mocked end-to-end tests pass for the implementation slices required by the MVP definition of done.

## Open questions
- How broad should `majówka` expansion be by default when adjacent weekend or bridge days are configurable?
- Should the first observation-provider iteration ship with a maintained local IMGW station metadata map, or is a fallback station-selection heuristic acceptable for MVP?
- Which scheduler mechanism should own periodic rule evaluation and warning polling in the first production-like stack?
- Should static notification commands remain fully deterministic while free-form conversation always routes through LangGraph, or can some intents bypass the graph for simplicity?

## Risks
- Public provider APIs may change shape, rate limits, or availability, creating instability in forecast, observation, or warning adapters.
- Date resolution for colloquial Polish phrases can produce user-visible ambiguity if the resolver rules are not tightly specified and tested.
- LLM-generated CEL proposals may be syntactically valid but semantically unsafe unless validation and allowlists are strict.
- The end-to-end surface area is large for an MVP, so weak contract discipline could cause integration churn across domain, graph, and persistence layers.
- Homelab deployment can hide operational issues such as clock drift, missing secrets, or database persistence mistakes until late integration testing.
